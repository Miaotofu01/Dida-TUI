# 网络层永远是全量刷新，增量只发生在本地

滴答清单 Open API 不提供任何「自某时刻起发生了什么变化」的接口：没有 changed-since，没有可用的条件请求语义（任务响应里确实带 `etag`，但文档没有说明如何使用它），也没有 webhook。任务上的 `startDate`/`endDate` 过滤针对的是**任务自身的日期字段**，而不是「任务何时被修改」——所以拿「上次同步时间」当短窗口去拉未完成任务，会静默漏掉那些「日期在很久以后、但刚刚被改过」的任务。窗口越短，漏得越多，而且不报错。

因此未完成任务的唯一可靠来源是逐清单的 `GET /open/v1/project/{id}/data`（只返回未完成任务、无分页）。拿回全量后在本地比对，只把差异写进本地库：**增量是本地存储层的概念，不是网络层的**。日期窗口只用于已完成任务——`POST /open/v1/task/completed` 按 `completedTime` 过滤，那是任务上唯一可被服务端过滤的变化时间戳，也是唯一允许使用时间游标的数据流。

**考虑过的替代方案**：用 `POST /open/v1/task/undone` 的 14 天窗口代替逐清单全量。否决理由是窗口外的任务和无日期任务会静默消失，而这种消失不会以任何形式报错，只会在某天表现为「我的任务不见了」。任何试图把逐清单全量「优化」成窗口查询的改动，都会重新引入这个 bug。

**第二个被否决的替代方案：`POST /open/v1/task/filter`（已实测）。** 跨清单批量读是存在的——省略 `projectIds` 时它返回**所有可访问清单加上收集箱**的任务（实测 10 条未完成、覆盖 2 个容器，与逐清单拉取的结果逐条一致；空 body 同样返回全量）。但它**硬顶 200 条且没有分页参数**，而 `status: [2]` 在一个已有 200+ 条已完成任务的账户上直接返回满 200 条——**它会在不报错的情况下截断**。所以它适合做一次性的跨清单查询，**不能**替代逐清单全量：被截断的那部分会静默消失，正是本 ADR 要防的那个 bug。

两条配套实测事实：`GET /open/v1/project` **不包含收集箱**，所以「1 + N」里的那个 +1 是必需的（`GET /open/v1/project/inbox/data` 接受字面量 `inbox`）；而服务端为收集箱里的任务返回的 `projectId` 是**每账户不同的字面量**（形如 `inbox1025205395`），不是 `inbox`。归类任务时必须用服务端返回的那个 id，拿 `"inbox"` 去比对会一条都对不上。

# 视觉身份：跟随终端主题、动效、以及上下两行的分工

v2 的界面一直是「功能先落地、样子随缘」：真正属于仓库的 CSS 只有三条规则（`tui/app.py:94-102` 的
`CursorPage` 与 `#status-bar`，`tui/overlays.py:24-41` 的浮层块），其余全是 Textual `textual-dark`
主题的默认值。真实使用后用户判定它**不够酷炫、偏冷**。本 ADR 记四条决定，四条都难逆转、且不写下来
后人会看不出理由。落地工单是 #51（视觉地基）与 #52（收尾打磨）；三版视觉语言的原型与最终取舍会记在
#51 的评论里。

## 一、跟随终端主题，而不是 app 自有调色板

**实测推翻了一个一直写在文档里的假设。** `docs/architecture.md:36` 写着「颜色只用终端 16 色（CSS 里写
`ansi_*`），不写死 hex」，读起来像是「让终端主题说话」。事实不是：

- Textual 8.2.8 默认把每一个 `ansi_*` **改写成真彩色**再发出去。`App.ansi_color` 默认 `None` →
  `native_ansi_color` 为 `False` → `ANSIToTruecolor` 以 `enabled=True` 构造，配色表是内建的 **Monokai**
  （`textual/theme.py:40`、`app.py:611`、`_ansi_theme.py:22`）。
- 实测同一条 CSS：默认下 `color: ansi_cyan` 出去是 `\x1b[38;2;88;209;235`（Monokai 的 `#58D1EB`）；
  设上 `App(ansi_color=True)` 之后出去是 `\x1b[36m`——**一个真正的 ANSI 码，由终端主题决定。**
- 所以那条规则「在源码里成立、在像素上不成立」。一个荒谬的具体后果：`PENDING_STYLE = "bold yellow"`
  实际渲染成 **`#FD971F` 橙色**。
- app 实际只画四种颜色：`#121212`、`#1E1E1E`、硬青 `#58D1EB`、橙 `#FD971F`。**一个硬青压在中性暗底上，
  这就是「冷」的全部来源**——而用户的主题（kitty + Catppuccin Mocha）是柔和的暖色粉彩，从未被用到。

**决定：跟随终端主题**，设 `App(ansi_color=True)`。

代价与不变量：

- 观感随主题走。换主题它就变——这是特性，不是缺陷。
- **spec story 114 只要求键位跨终端一致，从未要求颜色一致**，所以「到处长得一样」不是目标，不必为它牺牲主题跟随。
- 用户的 16 色槽位中 8–15 与 1–6 同值，**加亮不带来任何颜色对比**。层级只能来自字重、`dim`、反色、下划线与
  留白。任何想靠「更亮」做强调的设计都做不到，这是硬约束。
- 从此 `ansi_*` 名字是**承重的**：任何一处 `rgb()`、`hsl()`、命名色或 `$` 主题变量都会偷偷把真彩色放回来。
  见第四条。

## 二、页面背景用 `ansi_default`

平移过渡需要页面有不透明背景（Textual 每帧重绘，滑走的那块会漏出后面的东西）。四个候选实测：

| 写法 | 发出 | 看到 |
|---|---|---|
| `ansi_default` | `\x1b[49m` | **终端自己的背景**（`#1E1E2E`）——既不透明又不覆盖主题 |
| `ansi_black` | `\x1b[40m` | `#45475A`，**比终端背景更亮的青灰板** |
| `black` | 真彩色 `#000000` | 纯黑，比主题更硬 |
| `$background` | 真彩色 `#121212` | Textual 自带主题，完全无视用户 |

**决定：`ansi_default`。** 它既填满区域（平移有东西可滑），又画的是用户自己的背景；app **不覆盖**终端背景。
浮层那种「抬起来的面」用 `ansi_black`——同一块青灰在这里是资产：比页面亮一层，读作浮起。

## 三、动效：横向平移、会追赶的光标、阈值之后的转圈

用户明确要动效，并接受代价。

- **换层 = 横向平移。** 这不是装饰：`enter` 压栈、`esc` 出栈是**导航栈**（见 GLOSSARY 的「导航路径」），
  左右平移正是这个语义的标准表达。早先把它当「层层深入」而选纵向，是把结构与行为混为一谈。
- **光标 = 选中立即到位，装饰性的光标条随后追上。** 终端**无法在两条之间画出半格**，所以「滑动」只能实现为
  一根独立的高亮条在动。于是必须定死一件事：**数据选中瞬间到位，滑动只是装饰**——否则那 ~100ms 里用户看到的
  位置与实际选中不一致，按下 `space` 会打中另一条。这不是手感问题，是看起来像 bug 的正确性问题。
  时长 ≤120ms。
- **同步 = 超过阈值（约 300ms）才出现转圈。** 否则每天早上启动都会看到一个转圈的东西，而「只有变化才写库」
  意味着大多数同步根本不需要它。
- **瞬时反馈走原生 toast**（`App.notify()`），不再靠改状态栏那一行字符串。spec story 43 要的「短暂的视觉反馈」
  今天只是一个字符串。注意：真 pty 下能渲染，`run_test()` 下不会挂载——**验收必须在真 pty 里做**。
- 配 `animations = auto|on|off` 开关，默认 `auto`（ssh / 低能力终端关掉）。

## 四、上下两行的分工，以及终于要做真的守卫

- **顶栏**说「你在哪」：词标 + 导航路径。**状态栏**说「数据怎么样」：已同步时刻 · 待推送数量 · 逻辑日。
  **去掉 Textual 的 Footer**——它显示的键位从此归按层的 `?`。底部原本其实是**两行**（状态栏在 Footer 之上），
  所以顶栏是拿 Footer 换来的，**chrome 净增 0 行**。
- **守卫要做成真的。** 现在唯一的守卫是 `tests/test_architecture.py:181-194` 对 `src/dida/tui/**/*.py` 的
  **hex 源码扫描**；实测 `rgb()`、`hsl()`、`red`、`$primary`、`color(6)` **全部通过**，渲染出来的调色板根本
  没被验过。既然如此，一条 `rgb()` 就能静默毁掉第一条决定。所以**加两条**：源码扫描扩到
  hex / `rgb()` / `hsl()` / 命名色 / `$` 变量；再加一条**渲染级断言**——真跑一次 app，断言强调色发出的 SGR
  是 `\x1b[36m` 而不是 `\x1b[38;2;…`。后者是唯一能证明主题真的在说话的测试。

## Consequences

- 视觉常量必须只有一个出处（`tui/theme.py`）。实测一次改版要碰五处：app 的 CSS、浮层 CSS、各页面约 20 处
  `Text(style=…)`、主题默认值、以及 `keys.py` 的排版算术；没有单一改动点，「跟随主题」会在五处各自漂移。
- 任何「靠更亮做层级」的设计都不可行（槽位 8–15 与 1–6 同值）。
- **逾期标红在视觉地基里做不出来**：`TaskItem`（`read.py:196-224`）没有 overdue 位，TUI 也不许判断日期
  （架构规则）。地基只提供 `overdue` 语义 token，实现归 #37，接上归 #52。
- 字形宽度是新的承重项：`☰` 被 rich 算成 2 格而其实是东亚中性宽度，**一旦引入对齐列就会错位**；用户
  `LANG=zh_CN.UTF-8`，东亚**歧义**宽度的字形（`▣ ★ · ─ │ ╭╮╰╯ ↑↓`）在 CJK 字体下会变双宽。结构字形必须宽度
  无歧义，Nerd Font 图标（用户已装 FiraCode NF）只许出现在错了也不破对齐的装饰位。
- **截断与折行按页分工**：清单列表页与任务列表页**截断**（按单元格裁、带省略号 `…`，且丢弃顺序是
  标签 → 重复/提醒标记 → 截止时间 → 最后才截标题）；**任务详细页自动换行**。理由：列表要能一行一条地扫视，
  而详细页存在的意义就是读完整的——截断放错地方会变成「哪儿都读不全」。代价是详细页的字段行高度可变，
  光标与滚动必须按**屏幕行偏移表**算，不能再假设「一个字段 = 一屏一行」；这条归 #43。
- 这次改动**不碰信息架构与键位流程**，所以 #35–#48 的验收标准全部有效。

本 ADR 由 #51 / #52 落地。四条决定都是与用户逐条确认过的，不是实现者自选；每条后面的实测数字都可以
在本仓库自己的 venv 里重跑（`ansi_*` 的 SGR、四种背景写法、`PENDING_STYLE` 的实际颜色）。

# 写操作立即推送，完成不可逆

滴答清单 Open API 没有「取消完成」接口：`status` 不在 Create/Update 的参数表里（只有子任务的 `items[].status` 可写），删除也没有任何恢复接口。也就是说，用户在界面上按下 `x` 的那一次完成，在服务端是一个不可撤销的事实。

我们选择**立即推送**，而不是「本地先生效、防抖后再推、期间可撤销」。理由是延迟推送会让服务端在一段时间内保持旧状态，而在这个窗口里，任何一次同步都会让用户看到自己的操作「没生效」；同时这个 app 的定位是键盘快速分诊，一次按键的手感比可撤销性更值钱。

补偿措施：`x` 不与导航键相邻；完成成功后短暂高亮。按错时的逃生舱是官方客户端（它支持取消完成）——零成本，代价只是离开键盘。

**冲突裁决的例外**：待推送改动豁免于「服务端权威」。一次推送失败会让改动滞留在重试队列里，此时服务端仍是旧值；如果没有这个豁免，下一次全量刷新就会把用户刚做出的操作撤销掉。豁免的代价是本地状态可能比服务端新，所以状态栏必须常驻显示待推送数量。

**待验证的恢复路径**：`POST /open/v1/task/batch` 接受完整的 Task 结构（含 `status`），文档没有说明它是否被采纳。如果实测 `status=0` 生效，本 ADR 的结论不变（写仍然是立即推送），只是多一条键盘内的恢复路径。

**更新语义（已实测，工单 #22）**：`POST /open/v1/task/{taskId}` 的请求体里**省略的字段被保留**，不是全量替换。实测方法：建一个字段齐全的临时任务（`content`、`desc`、`priority=3`、`tags`、两个子任务），然后只发 `{id, projectId, dueDate}`，再回读逐字段比对。结果 `content` / `desc` / `priority` / `tags` / `items` / `status` / `title` / `timeZone` / `repeatFlag` / `isAllDay` 全部保留，只有 `dueDate` 按预期改变。

两处需要留意的观测，不要把它们的含义放大：

- 服务端在写入 `dueDate` 时**自动补了同值的 `startDate`**。`startDate` 由 `null` 变成 `2027-01-15T09:00:00.000+0000`，与 `dueDate` 相同。文档没有说明这件事，所以**在别的路径上不能假定它总会发生**（它可能是这次的特定行为）。如果确实总会发生，那么给一个没有 `startDate` 的任务写 `dueDate` 会顺带给它一个开始时间。
- `items` 被判为「变化」而出界，说明服务端对子任务数组做了规范化（键集合/默认值），**不是**清空——前后子任务 id 一致、数量一致。文档没写归一化的具体规则。

结论对本 ADR 不变，对写路径有一处影响：**「服务端快照 + 本次改动合并后再发」这个做法依然是当前实现，但它现在是一条保守选择，而不是必需**。只发改动字段在实测语义下同样正确。保留合并式写法的理由是它同时承载了「未知字段必须原样带回」（spec 的「如实呈现」），那条要求与本条实测无关，仍须遵守。

关于请求动词：官方文档里**不存在** `PATCH /open/v1/task/{id}`，更新走 `POST`。这一点一度是本工单的前提，实测前已按文档纠正。

**逃生舱的确切形态（已核实）**：官方桌面客户端不接受任务深链。从官方 Electron 包（中文 `dida 8.0.20`、英文 `ticktick 8.0.11`）里提取的证据是：`dida365://` 这个 scheme 不存在（包里只有 `ticktick://`），Linux 版 `.desktop` 没有注册任何协议处理器（无 `MimeType=`），主进程没有 `setAsDefaultProtocolClient` 且不处理 argv。唯一可用的形态是厂商自己在「复制任务链接」里生成的那条网页版路由——`https://dida365.com/webapp/#p/{projectId}/tasks/{taskId}`（`projectId` 含 `inbox` 时替换成字面量 `inbox`）。

它是纯客户端 hash 路由，URL 里不含凭据，能否打开任务取决于浏览器里是否已有登录态。因此这个逃生舱是「按一个键，开一个浏览器标签页」，不是「切到桌面 App」。

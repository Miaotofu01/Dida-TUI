# 换绑 = 验证 → 清库 → 重拉，无条件、不可恢复

「换绑账号」：把这个 app 连的滴答清单账号换到另一个。用户选的口径是**单账号覆盖式**——旧的作废，不并存、不切回。

## 一、为什么「清不清库」根本不是可选项

本地副本没有账号维度。`cache.sqlite3` 的七张表（`lists` / `tasks` / `pending_changes` / `pending_list_changes` / `sync_state` / `views` / `id_aliases`，`storage/store.py:96-154`）里**没有任何一列记着「这是谁的」**，库文件的路径也只由 `config_path()` 决定（`bootstrap.py:124-126`）。换掉 token 之后如果不清库，下一次全量刷新不会把它洗干净，而是会留下五样东西：

| 留下的 | 为什么洗不掉（`storage/store.py` / `sync/`） |
|---|---|
| 旧账号的**收集箱行** | 剪枝对 `is_inbox` 豁免（`:1095-1101`）。新旧两个 `inbox<digits>` 会并存，而 `_resolve_inbox` 只挑一行（`read.py:360-370`）——新收集箱可能被旧行遮住 |
| 旧账号的**已完成任务** | 剪枝明确跳过 `status == 2`（`:1121-1127`），已完成流只写不剪 |
| 旧的**完成游标** | 全量刷新把旧 `completed_cursor` 原样写回（`refresh.py:153-159`）；新账号在游标之前的完成记录**永远拉不到** |
| 旧的**待推送改动** | 队列表没有账号维度，只有逐条 resolve 才删（`:648-651`、`:893-896`）；下一轮 `push_pending` 会用**新 client** 推旧记录——旧清单 create 会在新账号真的建出来，落在收集箱的任务 create 用字面量 `inbox` 也会落到新账号 |
| 旧的**自定义视图** | `views` 表不被刷新删改；但 `ViewDefinition.lists` 存的是旧账号的 project id，匹配不到新任务 → 一串空视图 |

所以「不清库」不是一个保守选项，它是一串**静默串号**。清库不是省事，是唯一正确的做法。

## 二、决定

1. **触发**：个人主页上的「换绑」（ADR-0010）。它在清单列表页用 `A` 进入，覆盖层里粘贴 token。
2. **无条件清**：新 token 通过 `list_projects` 验证之后，**不问是不是同一个账号**，一律清库重拉。理由见第三节。
3. **不可恢复**：旧副本**不留备份**（用户明确决定：「不保留备份，不需要恢复」——自动备份曾是备选，被推翻）。
4. **丢了什么要说出来**：确认页先列出影响面——N 个清单 / M 条任务 / V 个自定义视图 / K 笔待推送——再要求用户**输入 `yes`**。因为这一步之后就没有回头路。
5. **顺序**（失败时把损失压到最小）：验证新 token → 确认 → **删库** → 写配置 → 重建。
   - 验证失败：磁盘一动不动（沿用 ADR-0003 的「先验证、后落盘」），停在输入框。
   - 删库失败：配置没动，旧账号完好，报错重来。
   - 写配置失败：库已经没了，但**配置仍是旧账号**——重开是旧账号 + 空库。这是三个失败点里最轻的一个，而且此时屏幕上必须把这句话说出来。
6. **重建方式**：**同一进程内重跑一遍启动序列**——app 退出 → `main` 再 `build_engine` / `build_app` → `run()`。屏幕闪一下，换来的是「不可能留下一个还在跟旧账号说话的半截状态」。反面是不退出、在引擎内部换掉 `store` / `client`：不闪屏，但引擎里的缓存、周期泵、日界重读每一处都要确认跟着新库，**漏一处就是静默串号**。`Store` 至今没有 `close()`，原地换还会让旧连接继续写一个已经解链的 inode。
7. **换绑之后**：立刻跑一次全量刷新并显示进度；落在个人主页，显示「已换绑到新账号」（用户要求）。

## 三、为什么是「无条件」，不是「想办法判断是不是同一个账号」

官方 API **没有「当前用户」端点**：`list_projects` 返回 200 只证明 token 有效，不证明它属于哪个账号（`notes/openapi-dida365.md:115-126`、`:1138-1173`）。唯一可能当指纹的是收集箱 id（`inbox<digits>`，每账户不同），但它**只在收集箱非空时才拿得到**（`refresh.py:288-292`、`read.py:354-355`），而一个新账号的收集箱完全可能是空的。

被否掉的三条：

- **用收集箱 id 当弱指纹**：能省掉一次误删，但空收集箱时判不了，只能退回「一律清」——于是这条分支既拿不到保证，又要多写一套测试。
- **问用户「这是同一账号重贴吗」**：把 API 的缺陷转嫁给用户，而用户很可能也不知道。
- **拆成两个动作（换绑清库 / 重贴不清库）**：两条路都是「换 token」，用户分不清该点哪个；点错的那一半要么串号，要么白丢数据。

**代价是明摆着的**：token 轮换（同一个账号重新发一枚）也会清库、也会丢自定义视图。这一条用户明确接受了。

## 四、后果

- **自定义视图会消失**，且没有恢复路径。它们是纯本地资产（ADR-0005），换绑是它们唯一会死的场景。
- **token 失效后的自救也走这条路**（状态栏那句「凭据失效，请重新粘贴 token」现在有了去处），代价同上。
- 首次运行**不搬**进这个覆盖层：`token` 为空时仍旧是启动前 `getpass` 粘贴（`bootstrap.py:237-253`）。代码里因此有两条输入 token 的路径，这是有意的——一条在 Textual 起来之前，一条在它里面。
- 分票：**这张票只做「个人主页骨架 + 换绑」**；统计与热力图另开一张（纯读，零破坏性，可以慢慢做）。骨架票**不预留**统计区的位置，避免交付一个残缺布局。

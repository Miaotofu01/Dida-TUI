## #46 — 逻辑日改了立刻生效，不用重启

Worktree `t46`, branch `ticket/46-live-day-boundary`.

**The problem is structural, not a missing reload.** The config is read once at startup and the boundary is
baked into the engine when it is constructed, so there is no re-read path at all.

Your ticket explicitly says **deciding *when* to re-read is a design decision, not a patch** — 「何时重读配置由
这张工单定（按 `r`？窗口获得焦点时？文件 watch？）」 — and requires you to **write the candidates and their
costs into the closing note before choosing**. Do that: name the options, say what each costs (a file watcher is
a dependency and a background thread; focus events are unreliable in some terminals; `r` is explicit and free but
only fires when the user asks), pick one, and justify it. Do not silently pick the cheapest.

Then: re-derive the current logical day, and let the UI **recompute without losing the cursor** — your AC.
「今天」 view, overdue classification and the defer arithmetic must all follow the same logical day, so all three
re-derive together. Note `defer`'s target is 「下一个逻辑日」 (#40's area) — don't change its behaviour, just make
sure it reads the current boundary rather than a stale one.

Related: the config file is the one holding the user's token. **Never read, print, or echo
`~/.config/dida-tui/config.toml`**; work through `dida.config`'s API. Test with a temp path.

AC worth calling out: 「有测试覆盖「改配置 → 逻辑日变化 → 视图跟着变」」 — an end-to-end-ish test at the engine
seam, not three unit tests that each pass while the wiring is broken.

## #47 — 退出拦截：`q` 与 `Ctrl+C` 都不能静默丢改动

Worktree `t47`, branch `ticket/47-quit-interception`.

**The bug is a second exit path.** `q` is already intercepted when there are pending changes, but `Ctrl+C` takes
a different default path and is not — a silent back door that loses the user's offline edits. Your ticket asks
both to run **the same judgement**.

Two things to know before you start:

- **A related guard landed just before your ticket.** The retry-queue pump's teardown race was fixed, and the
  general rule it established is: **after every `await`, ask `self.is_running` before touching the DOM.**
  `Timer._tick` swallows callback exceptions, so this class of bug surfaces as a teardown error far from its
  cause. Your confirm-then-exit flow awaits; make sure it obeys that rule. See `progress.md`.
- **Copy already exists and was reviewed.** A quit prompt with 「N 处」 and 「下次打开」 wording is pinned by
  tests, and one of them asserts the wording never implies the changes are lost — they are not, they are in the
  local store and the next launch retries them. Reuse that wording and keep those assertions alive; the files
  they live in may have been deleted by #34, in which case the conclusion needs re-expressing somewhere that
  survives. Check before assuming.

AC: with N pending, both `q` and `Ctrl+C` are intercepted and say how many; after confirmation the app exits;
with nothing pending, both exit directly. **Test all four combinations** — the two interception cases are the
ones your ticket exists for.

## #48 — 终端上的键：键位表守卫 + 分层帮助

Worktree `t48`, branch `ticket/48-keymap-guard-and-layered-help`.

**You own the single bindings table.** #34 created `tui/keys.py` as one data structure keyed by layer, precisely
so that help is derived from it rather than hand-copied — your AC 「帮助里列出的键与真实绑定一致（跟着绑定表走，
不是手抄一份）」 depends on that seam existing. If #34 produced something else, adapt to it rather than adding a
parallel list.

**The guard test must assert ABSENCE, not presence.** This is the subtle part and the reason the ticket exists:

- `Binding("ctrl+enter", ...)` **constructs and does fire** when such an event is dispatched — so a test that
  merely checks "the handler exists" passes while the real terminal can never deliver the key. Measured:
  `notes/terminal-input-evidence.md` §2 / `verify.py` section C.
- The honest assertion is that the keymap contains **no** unreliable key: `ctrl+enter`, `alt+enter`,
  `ctrl+shift+*`, `alt+arrow`. Measured reasons, all in `terminal-input-evidence.md`: plain `Enter` and
  `Alt+Enter` both arrive as `enter` (textual#6663 — so `alt+enter` would silently trigger the *wrong* action);
  `ctrl+enter` reaches Textual **only** through the kitty protocol we deliberately disable (ADR-0006), and under
  xterm `modifyOtherKeys` it arrives as `ctrl+\r`, not `ctrl+enter`.
- Your AC asks you to **self-check the guard by making a deliberate bad change and watching it fail.** Do that,
  and report the evidence — an untested guard is exactly the thing that rots.

**Also verify the connection to ADR-0006:** with the kitty push off, the help must not list any key that depends
on it. ADR-0006 is the reason the key list is restricted at all; if the flag is not actually being set (it was
missing from `src/` entirely until #34), that is worth reporting rather than assuming.

**Layered help.** `?` shows only the current layer's keys — three layers, three lists, derived from the table.
Not one big mixed table (that is v1's behaviour and an explicit non-goal). Assert per layer.

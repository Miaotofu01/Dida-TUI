## Problem Statement

用户用滴答清单管理任务，但官方客户端全是 GUI：启动慢、要点鼠标，在他自己的键盘工作流里（终端、编辑器、ssh 会话）切过去的成本很高。他想在早上花 30 秒把「今天该做什么」过一遍并完成分诊——完成、顺延、改期、调优先级——却没有任何终端内的入口。手机端适合随手收集，不适合批量分诊。

「今天」这件事本身也没有现成答案：滴答清单的 Open API 不提供任何服务端智能清单（没有 Today、没有 Next 7 days），客户端必须自己定义「今天」。而这个定义的核心恰恰是用户最私人的一个设定——几点睡才算新的一天。按自然日切，凌晨两点看到的「今天」就是错的。

更麻烦的是这个 API 的两个特性：一是有「完成」却没有任何「取消完成」接口，一个按错的键在服务端是不可撤销的事实；二是一串静默失败（非法日期被直接忽略、无日期的任务重复规则被清空、时区写错会静默位移），它们不报错，只在几天后表现为「任务怎么不对」。任何客户端都必须把这两件事当成设计约束，而不是事后补丁。

## Solution

一个单进程的终端应用，命令 `dida`，用 Python + Textual 写成。三栏：左栏清单、中栏任务列（逾期置顶 / 今日 / 收集箱无日期）、右栏常驻详情（描述、子任务、标签、备注）。

启动先把本地缓存渲染出来（秒开），后台做一次全量刷新。所有写操作立即推送到滴答清单，失败进重试队列并在状态栏常驻可见。逻辑日可配：默认 `24:00`（等于自然日），用户设成 `04:00` 时，凌晨两点看到的「今天」仍是他还没睡的那一天。

只用个人 API Token 认证——不需要注册 OAuth 应用、不需要回调地址、不需要刷新令牌。没有守护进程，没有开机自启：敲 `dida` 就开，按 `q` 就关。

## User Stories

### 启动与凭据

1. 作为首次使用者，我要在第一次运行时被提示粘贴个人 API Token，这样我不需要注册 OAuth 应用或配置回调地址。
2. 作为首次使用者，我要在保存 token 之前先被验证一次（至少能成功列出清单），这样我不会把一个错的 token 存下来然后对着一屏空白发呆。
3. 作为日常使用者，我要一启动就看到本地缓存立刻渲染出来，这样我不必为了看一眼今天的任务而等网络。
4. 作为日常使用者，我要启动后在后台自动做一次全量刷新，这样我看到的不是过期数据。
5. 作为日常使用者，我要在状态栏看到上次刷新时间，这样我能判断眼前数据的年龄。
6. 作为凭据失效的使用者，我要被明确告知并引导重新粘贴 token，而不是看到一个笼统的网络错误。
7. 作为使用者，我要配置文件权限是 0600，这样我的 token 不会被同机器上的其它用户读到。

### 逻辑日

8. 作为夜猫子，我要能配置「一天结束的时刻」（默认 `24:00`），这样我凌晨两点看到的「今天」还是我还没睡的那一天。

13. 作为使用者，我要在输入「明天」这类相对日期时，它们从当前逻辑日算起，而不是从自然日算起。

## Implementation Decisions

### 模块划分

七个模块，每个都是深模块：一个窄接口，行为藏在里面。

**配置与凭据**：一个 TOML 配置文件（`~/.config/dida-tui/config.toml`，权限 0600），存 token、逻辑日边界、刷新与推送开关、已完成区窗口。首次运行引导粘贴 token，并在写入磁盘之前用一次「列出清单」调用验证它。负责在文件缺失时生成默认配置。

**滴答 API 客户端**：窄接口——列清单、按清单取未完成任务、取单个任务、新建任务、更新任务、完成任务、删除任务、按完成时间窗口取已完成任务、列标签。内部承担：Bearer 认证、领域对象与 API 字段之间的映射、时区原样保留与回写、未知字段透传。它还承担三个**本地守卫**，因为服务端对这些错误是静默的：日期格式在发出前严格校验；没有截止时间或开始时间的任务绝不写重复规则；回写时把服务端返回的未知字段一并带回。传输层可注入，以便在测试里钉死请求形状。

**本地存储**：SQLite，用标准库。四类数据——清单、任务快照、待推送改动、同步状态。任务快照保留服务端原始字段（含未知字段）加本地元数据，以便无损回写。UI 不直接访问存储，只通过同步引擎。

**同步引擎**：全量刷新（逐清单取未完成 → 与本地快照 diff → 只写变化）、已完成流（按完成时间游标拉窗口）、重试队列（指数退避）、冲突裁决（服务端权威，重试队列里的待推送改动豁免）。对外只暴露：分组后的视图模型、写操作、以及状态（待推送数量、上次刷新时间、当前逻辑日）。

**逻辑日**：纯函数。输入一个时刻和边界配置，输出逻辑日区间（开始时刻、结束时刻、日期标签），以及一个时刻属于哪个逻辑日。

**日期解析器**：纯函数。输入一行文本，输出标题、可选截止时间、可选优先级、可选标签列表、以及解析诊断信息（哪些部分没被识别）。

**TUI**：Textual 应用。三栏 + 状态栏 + 帮助浮层。只通过同步引擎的接口读数据与发起操作，不做任何业务判断（分组、排序、逾期判定都在引擎里）。

### 架构决策

- 网络层永远是全量刷新，增量只发生在本地比对。见 `docs/adr/0001-full-refresh-and-local-diff.md`。
- 写操作立即推送，完成不可逆；补偿是防误按与官方客户端逃生舱。见 `docs/adr/0002-immediate-push-irreversible-complete.md`。
- 冲突裁决 = 服务端权威 + 待推送豁免 + 明确告知。
- 单进程、无守护进程、无开机自启。`q` 即结束。
- 只用个人 API Token（网页版「设置 > 账户 > API Token」），v1 不实现 OAuth：官方文档没有刷新令牌、没有 device code、也没写令牌有效期。
- Python 3.12 + Textual，以 `uv tool install -e .` 安装成全局 `dida` 命令。
- 只用终端 16 色，不写死十六进制颜色，以适配任意终端主题。

### 接口契约

- API 客户端把一切失败表达成结构化错误（网络失败、认证失败、服务端拒绝、字段被静默忽略），不把裸异常抛给 UI。
- 同步引擎的写操作是乐观的：先在本地生效、立即返回、把改动推进待推送队列。网络结果不是 UI 的前置条件。
- 同步引擎的读操作返回已分组的视图模型（逾期 / 今日 / 收集箱无日期 / 已完成）。分组、排序、逾期判定都在引擎内完成。
- 逻辑日、日期解析器、分组排序是无依赖的纯函数，可以直接测试。

### 配置 schema

| 键 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `token` | 字符串 | 无（必填） | 个人 API Token |
| `day_end` | 字符串 | `"24:00"` | 逻辑日边界时刻。`"24:00"` 与 `"00:00"` 等价，都表示不偏移；`"04:00"` 表示逻辑日 D 从 D 当天 04:00 持续到次日 04:00 |
| `refresh_on_start` | 布尔 | `true` | 启动时自动全量刷新 |
| `push_on_change` | 布尔 | `true` | 界面上的改动立即推送 |
| `completed_window_hours` | 整数 | `24` | 已完成区往回看多少小时 |

`day_end` 的取值必须在 `00:00` 到 `24:00` 之间，且必须能被解析成整分钟。

| `x` / `Space` | 完成（立即推送） | `Enter` | 开合右栏详情 |

### 日期解析器语法

| 输入 | 含义 |
| --- | --- |
| `今天` / `今日` | 当前逻辑日，无具体时刻 |
| `明天` / `明日` | 下一个逻辑日 |
| `后天` | 下两个逻辑日 |
| `周X` / `星期X` | 该星期几；若当前逻辑日就是它，取今天 |
| `下周X` | 下一个自然周的该星期几 |
| `+3d` / `+3天` | 当前逻辑日 +3 天 |
| `3-15` / `3/15` | 本年 3 月 15 日；若已过去则取下一年 |
| `14:00` / `下午3点` / `晚上8点` | 给已解析出的日期补时刻 |
| 只给时刻且该时刻已过 | 落到下一个逻辑日 |
| `!高` / `!中` / `!低` | 优先级：高 / 中 / 低 |
| `!1` / `!2` / `!3` | 优先级：低 / 中 / 高（数字是**档位序号**，不是 API 的 `priority` 取值） |
| `#标签` | 标签 |
| 其余文本 | 标题 |

解析器必须返回诊断信息：如果用户写了疑似日期但没能解析（例如 `13-45`），UI 要明确提示，而不是把它当标题的一部分静默吞掉。

解析器的边界规则：

- **数字是档位，不是 API 取值。** 滴答清单 API 用 `0/1/3/5` 编码无/低/中/高，但那套编码是线上实现细节，不作为用户语法暴露。所以 `!1`=低、`!2`=中、`!3`=高，与 `!低`/`!中`/`!高` 一一对应，也与 `p` 键的循环顺序（无→低→中→高）一致。**`!5` 不是「高」。**
- **不提供清除优先级的语法。** 新建的任务本来就没有优先级，清除是 `p` 键的事；`!0` 属于下面那条「不认识的写法」。
- **`!` 后面紧跟 `高`/`中`/`低` 或一个数字时，一律当作优先级记号去解析。** 数字不是 1/2/3（含 `0`、`4`、`5`…）时进诊断，提示「优先级只支持 `!1`/`!2`/`!3` 或 `!高`/`!中`/`!低`」，**不静默当标题文本**。
- 不识别 `!high` 这类英文写法（v1 不发明语法）：`!` 后面是字母时按普通文本处理。
- 优先级记号可以出现在任意位置，位置不影响含义；解析器把识别到的记号摘掉，其余部分按原顺序拼成标题。
- 同一行里优先级记号重复出现时，取最后一个，并进诊断告知。
- `#` 后面跟一段不含空白的文本即为标签，可出现多个；`#` 后紧跟空白或行尾时按普通文本处理。**已知副作用**：「修 #1 bug」里的 `#1` 会被当成标签。

### 本地存储 schema

- **清单**：id、名称、颜色、排序、所属项目组、是否收集箱。
- **任务快照**：id、清单 id、标题、描述、备注、截止时间、开始时间、是否全天、时区、优先级、标签、子任务数组、重复规则、重复来源、状态、完成时间、排序、以及服务端返回的原始字段集合。
- **待推送改动**：任务 id、改动种类、载荷、创建时间、尝试次数、下次重试时间、最后一次错误。
- **同步状态**：已完成流游标、上次刷新完成时间、上次计算出的逻辑日。

## Testing Decisions

**什么算是好测试**：只断言外部行为——按键之后的屏幕文本，以及假后端收到的调用序列。不断言私有方法，不断言整屏快照（否则每次调样式都要改测试），不 mock 项目自己的模块。

**接缝一（主接缝，最高）**：TUI 应用 + 内存假后端，用 Textual 自带的测试 pilot 驱动。一个测试可以完整走通「按 `x` → 假后端收到 complete 调用」。要覆盖的行为：键位、三栏渲染与降级、逻辑日边界、乐观更新、重试队列、待推送豁免、退出警告、子任务的写前重读。

**接缝二（窄接缝）**：HTTP 传输层可注入。只钉两类东西：请求形状（方法、URL、认证头、请求体字段），以及静默失败守卫（非法日期在本地被拦、无日期任务不写重复规则、时区原样回写、未知字段透传）。不在这里测业务逻辑。

**无接缝（纯函数，直接测）**：逻辑日、日期解析器、分组与排序。这些不需要任何假件。

**必须可注入的时钟**：逻辑日判定与重试退避都依赖「现在」。这是唯一一个纯粹为了可测性而引入的依赖，测试必须能控制它。

**要测的模块**：同步引擎（最重要，行为最多）、日期解析器、逻辑日、TUI 的键位与渲染、API 客户端的请求形状与守卫。

**先例**：仓库目前是空的，没有任何测试。这个 spec 建立先例，后续工单沿用这两个接缝。

## Out of Scope

- 守护进程、开机自启、桌面通知。v1 是纯前台进程，`q` 即结束。
- OAuth 授权码流程（只用个人 API Token）。
- 习惯打卡、专注/番茄钟、倒计时、评论、附件、看板列、项目组管理。
- 标签的修改与删除（API 只支持新建与列出）。
- 重复规则的编辑，以及跳过某一次重复。
- 回收站列表与恢复删除（API 没有这个能力）。
- 完整的多端合并：只有服务端权威加待推送豁免，没有字段级的合并界面。
- 鼠标操作。
- Windows 与 macOS 的打包和系统集成（主目标是 Linux）。
- 多账号。

## Further Notes

### 待实测的事实（都不阻塞开工）

1. `POST /open/v1/task/batch` 携带 `status = 0` 能否取消完成。方法：建临时任务 → 完成 → batch 回写 `status=0` → GET 看状态。若成立，就多一条键盘内的恢复路径；ADR-0002 的结论不变（写仍然是立即推送）。
2. `etag` / `If-None-Match` 是否真的生效。方法：GET 一个任务拿到 `etag`（响应里的 `id2etag`），带 `If-None-Match` 再 GET，看是否 304。若生效，未完成那一路也能省下流量。
3. `task/completed` 与 `task/filter` 文档里写的「≤200」到底是入参上限还是返回上限。
4. `task/undone` 的日期窗口过滤的是开始时间还是截止时间（决定它能否作为快路径使用）。
5. `task update` 的 PATCH 语义：省略的字段是否真的被保留。
### 已核实：任务深链

从官方 Linux 桌面客户端包里提取出的**厂商自己的「复制任务链接」模板**（英文包 `ticktick-8.0.11` 与中文包 `dida-8.0.20` 的 `opt/*/resources/app.asar`，两处逻辑一致；主机名来自构建配置 `site_domain`，中文版即 `dida365.com`）：

```
https://dida365.com/webapp/#p/{projectId}/tasks/{taskId}
```

- `projectId` 里包含 `"inbox"` 时，按厂商逻辑替换成字面量 `inbox`。
- `projectId` 为空或未知时的兜底：`https://dida365.com/webapp/#q/all/tasks/{taskId}`。厂商自己不为任务链接生成它，但同一个 react-router 配置里存在 `q/:name/:type/:id` 路由，结构上有效。
- **`dida365://` 这个 scheme 不存在**，官方包里只有 `ticktick://`。
- **Linux 桌面客户端不注册任何协议处理器**：两个官方 `.desktop` 文件都没有 `MimeType=`，主进程没有 `setAsDefaultProtocolClient`、没有 `open-url`，`second-instance` 忽略 argv。所以 `ticktick://` 在 Linux 上打不开 App，`o` 键不要尝试唤起桌面客户端。
- 官方文档**从未记载任何网页 URL 形态**；只有 iOS 的 URL scheme 有文档，且其中没有「打开指定任务」这一条。
- 深链是**纯客户端 hash 路由，URL 不含凭据**：只有浏览器里已有登录态时才打开任务，否则落到登录页（未登录访问 `/webapp/` 会 302 到营销页）。因此 `o` 键的正确行为是「把 URL 交给系统浏览器」。
- 第三方实现走的就是这两个形态（Raycast 的 dida365 扩展、TickTickSync、obsidian-dida365-link），其中 obsidian-dida365-link 与厂商逻辑完全一致。

置信度说明：hash 片段从不发给服务端，所以 `curl` 永远无法证明一条路由。上面的结论来自厂商与第三方**源码**，不是实测点击。

### 已知陷阱（客户端必须在本地防）

- 非法日期格式被服务端**静默忽略**，不报错。
- 没有日期的任务，重复规则会被**静默清空**。
- 提醒字段能写入，但官方客户端里的显示可能错乱。
- 文档说 `task/filter` 的标签过滤是「全部包含」，实测是「任一匹配」。
- 官方文档没有刷新令牌、没有 device code、也没写令牌有效期，所以 v1 不碰 OAuth。
- 文档入口是 `https://developer.dida365.com/docs/openapi.md`；`https://developer.dida365.com/docs` 本身返回 404（是个 SPA）。

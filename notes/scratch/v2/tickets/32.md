## What to build

这张不改变任何用户可见行为。它的价值是让后面每一张写路径工单不必先读懂一整块代码，也不让 v1 的结论随界面一起被丢掉。

**1. 写类型只留一处。** 引擎侧的写类型与存储侧的变更类型成员完全重复（四个成员一一对应），于是「新增一种写」要在四个地方各改一次。把它们合成一处，让后面新增写类型只改一个地方。

**2. 大模块按职责切开。** 同步引擎与界面模块都很大，而且里面按工单分段——同一段代码同时承担好几个不相干的变化原因。按职责切开，让后续工单能只读自己那一块。

**3. 先搬后删。** v1 有 521 条测试，其中 203 条随界面重写作废，但这 203 条里混着约 50 条其实是引擎/API 级的断言（同步、写路径、刷新、守卫的结论）。**先把这些断言搬进不依赖界面的测试文件，再让界面重写那张工单去删那 203 个文件。** 不要连结论一起丢掉。

顺带查清日期解析器当前的全部消费者，写进这张工单的收尾说明——v2 整体作废日期解析器，但它现在还被引擎的速记与改期路径用着，界面重写那张工单要照着这份清单删干净。

## Acceptance criteria

- [ ] 新增一种写类型只需要改一个地方，不再四处同步
- [ ] 引擎与界面的两个大模块按职责切开，没有一段代码同时承担多个不相干的变化原因
- [ ] 界面测试里那约 50 条引擎/API 级断言已搬进不依赖界面的测试文件，断言的外部行为不变
- [ ] `uv run pytest` 全绿，测试数量不比搬之前少
- [ ] 收尾说明里列出日期解析器当前的全部消费者，作为删除时的核对清单

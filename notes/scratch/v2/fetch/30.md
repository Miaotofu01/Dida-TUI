## Problem Statement

我用滴答清单管理任务，但官方客户端全是 GUI：启动慢、要点鼠标，在我自己的键盘工作流里（终端、编辑器、ssh 会话）切过去的成本很高。所以我做了 `dida`——一个终端客户端。

**v1 做出来的是「今日执行台」，它不可用。** 它只能看到今天的任务：清单栏只是个带数字的装饰，光标能在上面移动但没有任何作用，进不去任何清单，也没法往指定的清单加任务。事实上我连一条任务的标题都改不了——右栏是只读的，整个界面能写的只有「完成」「顺延」「改优先级」「新建到收集箱」「删除」。

我要的不是「把今天这一屏做到极致」，我要的是**和滴答清单网页版同款的任务视野**：能选清单、能进入清单、能看到这个清单里的全部任务、能新建和编辑。这些都是最基础的东西，v1 一个都没有。

## Solution

一个单进程的终端应用，命令 `dida`，用 Python + Textual 写成。**一栏，三层页面**，`enter` 进入下一层、`esc` 退回上一层：

- **清单列表页**（启动落在这里）——内置视图、自定义视图、真实清单平铺成一列，用前缀区分类型；项目组显示成不可进入的小标题；收集箱置顶。上下选择，`n` 新建（清单或视图）、`e` 修改它的信息、`d` 删除、`enter` 进入。
- **任务列表页**——当前清单（或视图）里的全部任务，客户端统一排序（截止时间 → 优先级；无日期的排在有日期的后面，已完成的沉底）。上下选择，`space` 在完成与取消完成之间切换，`n` 新建、`d` 删除、`g`/`G` 顺延、`enter` 进入详细页。
- **任务详细页**——标题、描述、备注、所属清单、截止时间、优先级、标签；子任务只读显示。上下选择字段，`enter` 进入某个字段的编辑，编辑中 `esc` 结束编辑回到字段列表，在字段列表上 `esc` 退回任务列表。

**读是全部，写是核心**：所有清单、所有任务都读得到；完成 / 取消完成、改期、顺延、改优先级、改标题与正文、改所属清单、打标签、新建、删除都写得动。写操作立即推送到滴答清单，失败进重试队列并在状态栏常驻可见。

「今天」从整个 app 的定位降级成**三个内置视图之一**（今天 / 最近七天 / 所有）。可以自己建视图——它是一组保存下来的过滤条件，**只存在本地**，因为官方 API 没有任何「保存过滤条件」的接口。

只用个人 API Token 认证：不需要注册 OAuth 应用、不需要回调地址、不需要刷新令牌。没有守护进程，没有开机自启：敲 `dida` 就开，按 `q` 就关。

## User Stories

### 启动与凭据

1. 作为首次使用者，我要在第一次运行时被提示粘贴个人 API Token，这样我不需要注册 OAuth 应用或配置回调地址。
2. 作为首次使用者，我要在保存 token 之前先被验证一次（至少能成功列出清单），这样我不会把一个错的 token 存下来然后对着一屏空白发呆。
3. 作为使用者，我要配置文件权限是 0600，这样我的 token 不会被同机器上的其它用户读到。
4. 作为日常使用者，我要一启动就看到本地缓存立刻渲染出来，这样我不必为了看一眼任务而等网络。
5. 作为日常使用者，我要启动后在后台自动做一次全量刷新，这样我看到的不是过期数据。
6. 作为日常使用者，我要在状态栏看到上次刷新时间，这样我能判断眼前数据的年龄。
7. 作为凭据失效的使用者，我要被明确告知并引导重新粘贴 token，而不是看到一个笼统的网络错误。
8. 作为使用者，我要启动后落在**清单列表页**，而不是某个过滤视图上。

### 清单列表页

9. 作为使用者，我要用 `j`/`k` 和方向键在这份清单里移动光标。
10. 作为使用者，我要在一屏里同时看到内置视图、我自建的视图、以及真实清单，并且**一眼能分清它们不是同一种东西**（用前缀字符区分，不靠颜色单独承担）。
11. 作为使用者，我要**收集箱排在最上面**，因为它是随手记的默认落点。
12. 作为使用者，我要清单按项目组归拢，项目组显示成**不可进入的小标题**。
13. 作为使用者，我要每一行显示这个清单的未完成任务条数，这样我知道还剩多少。
14. 作为使用者，我要按 `n` 新建，并且**先被问一句「清单还是视图」**，因为这两者在后面完全是两种东西。
15. 作为使用者，我要在新建清单时输入名称，并且可以挑一个颜色。
16. 作为使用者，我要按 `e` 修改当前选中项的信息：清单改名称与颜色，视图改过滤条件。
17. 作为使用者，我要按 `d` 删除当前选中项，并且**要一次 y/n 确认**。
18. 作为使用者，我要删除清单时被明确告知它里面的任务会发生什么（服务端行为未知），这样我不会以为它只是「从列表里移走」。
19. 作为使用者，我要删除自定义视图时**不删除任何任务**，视图只是过滤条件。
20. 作为使用者，我要按 `enter` 进入选中的那一行；如果它是视图，进去看到的是过滤后的任务。
21. 作为使用者，我要光标跨刷新存活，这样后台刷新不会把我踢回第一行。
22. 作为使用者，我要在清单很多时能滚动，而不是只看得到前几屏。
23. 作为使用者，我要看到 `kind` 是 NOTE 的清单被标出来且**不可进入**，因为那种清单装不了任务，进去只会看到一屏空白。
24. 作为使用者，我要看到某个清单的 `permission` 不是 write 时被标出来，这样我知道为什么改不动它。

## Implementation Decisions

### 模块划分

七个模块，每个都是深模块：一个窄接口，行为藏在里面。前六个沿用 v1 的划分，新增第七个。

**配置与凭据**：一个 TOML 配置文件存 token、逻辑日边界、刷新与推送开关、已完成区窗口。首次运行引导粘贴 token，并在写入磁盘之前用一次「列出清单」调用验证它。配置文件里**不放视图定义**——视图是用户资产，存本地库。

**滴答 API 客户端**：在 v1 已有的九个方法（列清单、列标签、按完成时间窗口取已完成任务、取某清单的 data、取单个任务、新建任务、更新任务、完成任务、删除任务）之外，新增：清单的建 / 改 / 删 / 按 id 读；任务搬运（清单之间移动）；批量更新（**这是取消完成的唯一路径**）；按过滤条件查询任务；搜索任务。内部继续承担：Bearer 认证、领域对象与 API 字段之间的映射、时区原样保留与回写、未知字段透传。

**本地存储**：SQLite，用标准库。五类数据——清单、任务快照、**视图定义（新增）**、待推送改动、同步状态。任务快照保留服务端原始字段（含未知字段），以便无损回写；它现在也要存**已完成**的任务（清单里要划掉显示它们）。刷新时**要剪枝**：远端已经不存在的任务必须从本地删掉（v1 从不剪枝，这是要修的既有缺陷）。

**同步引擎**：一次全量刷新 = 清单索引 1 次 + 每个清单 1 次 + 收集箱 1 次 + 已完成流 1 次。读路径不再返回「今日视图」，而是返回**清单列表 / 某个清单或视图的任务列表 / 单条任务的详情**。写路径沿用 v1 的乐观入队 + 立即推送 + 指数退避重试 + 「待推送改动豁免于服务端权威」。

**视图求值**：一组**纯函数**——把一个视图定义 + 全量任务缓存 + 当前逻辑日，算成一份排好序的任务列表。不碰网络，不碰存储。内置视图（今天 / 最近七天 / 所有）就是三个写死的视图定义，走同一条求值路径。

**终端界面**：一栏、三层页面。三个页面各自是一个可聚焦的列表或表单，`enter` 向下、`esc` 向上。清单的建/改表单与视图的过滤条件表单是同一个浮层，按选中行的类型决定字段。

**终端能力守卫**：一处集中决定「哪些键可以用」和「kitty 协议推送开不开」。键位表只允许使用终端一定传得上来的键。

### 键位表

| 层 | 键 | 动作 |
|---|---|---|
| 全局 | `↑`/`↓`/`j`/`k` | 移动光标 |
| 全局 | `enter` | 进入下一层 / 提交输入 |
| 全局 | `esc` | 退回上一层 / 结束字段编辑 / 清空输入 |
| 全局 | `?` | 当前层的键位帮助 |
| 全局 | `r` | 手动同步 |
| 全局 | `q` | 退出（有待推送改动时先拦一下） |
| 全局 | `o` | 在浏览器里打开当前任务 |
| 清单列表页 | `n` / `e` / `d` | 新建 / 改信息 / 删除 |
| 任务列表页 | `space` | 完成 ↔ 取消完成 |
| 任务列表页 | `n` / `d` | 新建（只填标题）/ 删除 |
| 任务列表页 | `g` / `G` | 顺延一个逻辑日 / 一周 |
| 任务详细页 | `enter` / `esc` | 进入字段编辑 / 结束编辑或退回列表 |
| 任务详细页 | `d` | 删除任务 |

**明确不绑**：`ctrl+enter`（多数终端把它发成和 `enter` 同一个字节）、`ctrl+shift+*`、`alt+方向键`、`alt+enter`。它们要么收不到，要么会静默塌缩成不加修饰的键，从而触发错误的动作。

### 三层页面的状态机

- 启动 → 清单列表页，光标落在收集箱。
- 清单列表页：光标在一行上；`enter` → 任务列表页（记住是哪一行）；`e` → 信息/条件浮层；`n` → 先选类型再进同一个浮层；`d` → 确认后删除。
- 任务列表页：光标在一条任务上；`enter` → 任务详细页；`esc` → 回清单列表页（光标还原到进来的那一行）。
- 任务详细页：光标在一个字段上；`enter` → 该字段进入编辑态；编辑态下 `esc` → 结束编辑、回字段列表；非编辑态下 `esc` → 回任务列表页，光标还原到进来时的那条任务。

### 写路径的三处关键约定

- **完成走文档化的完成端点**（`POST /open/v1/project/{projectId}/task/{taskId}/complete`）。
- **取消完成走批量更新**（`POST /open/v1/task/batch` 的 `update` 数组带 `status: 0`）。这条路径官方文档**一字未提**，是实测确认的：批量更新带 `status: 2` 能把任务完成，带 `status: 0` 能把已完成的任务改回未完成。批量更新是**合并语义**（只发 `{id, projectId, status}`，标题/描述/备注/优先级全部保留）。实现时不要因为「文档没写」就把它删掉。
- **改所属清单走搬运端点**（`POST /open/v1/task/move`），不是把它当成一次普通的字段更新。搬运在收集箱与真实清单之间双向可用。

### 收集箱的身份

服务端的清单索引（`GET /open/v1/project`）**不包含收集箱**，所以客户端必须自己补上这一行；请求侧可以继续用字面量 `inbox`（取收集箱数据、完成任务、删除任务都接受它），但**服务端为收集箱里的任务返回的 `projectId` 是每账户不同的一串**（形如 `inbox` 加一截数字）。因此：归类、分组、计数一律用服务端返回的那个 id；拿 `"inbox"` 去比对会一条都对不上。这一条是实测踩出来的，不是推测。

### 视图定义

视图 = 一组过滤条件 + 一个名字。过滤维度：清单范围（多选）、截止时间的区间（相对逻辑日表达，例如「今天到期」「最近七天」「无日期」）、优先级（多选）、标签（多选）、完成状态。

**求值在本地**，对全量缓存做，因此日期条件过滤的是 `dueDate`——这与服务端的查询接口不同（那个接口的日期区间过滤的是 `startDate`，而且硬顶 200 条、没有分页，所以它根本表达不了「今天到期」）。

内置视图就是三个写死的视图定义：「今天」= 逾期 ∪ 截止于当前逻辑日（**含逾期，逾期置顶标红**）；「最近七天」= 截止时间落在从今天起的七个逻辑日内；「所有」= 全部未完成。

### 排序

客户端统一重排，不看服务端的 `sortOrder`：先按截止时间升序 → 再按优先级从高到低 → 无截止时间的排在有截止时间的后面 → 已完成的一律沉到最底。任务行在清单视图里不重复显示所属清单名，在视图里必须显示。

### 两个自由文本字段

API 有 `content` 和 `desc` 两个独立字段，两个都可写、互不覆盖。术语表把它们定成：**描述 = `content`**、**备注 = `desc`**。（v1 标反了，这份 spec 纠正它。经验证据：一个自带清单里的 7 条任务 `content` 全部非空、`desc` 全部为空，而它们在网页版上是有正文的。）

### 已完成

已完成任务要出现在清单里（划掉、沉底、只显示最近 7 天）。两处必须写清：

- 拉取按服务的完成时间窗口加 `status` 过滤**双重**条件——**取消完成之后 `completedTime` 不会被清空**（实测），只按时间筛会把已取消完成的任务又捞回来。
- 本地判定「已完成」一律看 `status`（`2` 是完成，`0` 是正常，`-1` 是已放弃），不看有没有完成时间。

### 终端能力

**启动时设上 `TEXTUAL_DISABLE_KITTY_KEY`**（关掉 kitty 键盘协议的推送）。原因不是洁癖：开着它，输入法一次上屏超过四个汉字就会被当成一个按键事件，而解析器的 32 字符阈值会让它放弃匹配、把整串逐字符当按键重发——中文直接变成乱码。代价是 `ctrl+enter` 收不到，而我们本来就不依赖它。**升级 Textual 之后要把中文输入当成一条验收项重跑**，上游修掉之前不要去掉这个开关。

`space` 有一个已知陷阱：输入框拿到焦点时它会被当字符吞掉，app 级绑定静默失效。所以完成键只在任务列表页有效，而那一页没有输入框抢焦点；输入框存在时一律走 `enter` 提交。

### 本地守卫（沿用并扩充 v1）

日期格式在发出前严格校验；没有截止时间或开始时间的任务绝不写重复规则；回写时把服务端返回的未知字段一并带回；时区原样保留并回写。传输层可注入，以便在测试里钉死请求形状。

### schema 变化

- 新增**视图**表：名字、过滤条件、排序。
- 任务快照新增对**已完成任务**的承载（清单里要划掉显示）。
- 刷新新增**剪枝**（远端已不存在的任务从本地删掉）。
- 清单记录补齐 v1 已经在存但没暴露出去的字段：颜色、排序、项目组、是否收集箱、`kind`、`permission`。

### 与 v1 的关系

v1 的代码在 `feat/v1-today-console` 分支上（PR #28），先合并它、再在它之上做 v2。**可以原样保留**：API 客户端的既有方法、传输层、错误类型、本地守卫、SQLite 存储、重试队列与冲突豁免、逻辑日、日期/时间的格式化纯函数、凭据引导与验证、深链拼装。**必须重写**：读模型（v1 的读路径只为「今日」服务，返回一个硬编码了三个分区的视图类型）、同步引擎的读入口与新建任务的落点（v1 写死收集箱）、整个界面层。**整体作废**：日期解析器。

## Testing Decisions

**好测试的判据**：只断言外部行为——「我在这一层按了这个键，下一层显示了这个」。不断言控件树、不断言内部状态对象、不断言渲染字符串里的空白与颜色码。一个测试要能在不读实现的前提下看懂它在验什么。

**两个接缝**（沿用 v1，已与用户确认）：

1. **主接缝——内存假后端 + Textual 的 `run_test()` pilot**。整个 TUI 跑在真的 Textual 上，底下换成一个内存里的假后端，于是「进入清单」「新建任务」「改字段」「完成与取消完成」这些跨页流程都能真的按键、真的看下一屏。这是覆盖率的主来源，也是唯一能测「三层页面的进出与光标还原」的地方。
2. **窄接缝——可注入的 HTTP 传输层**，钉死请求形状：取消完成必须打到批量更新并带 `status: 0`；改所属清单必须打到搬运端点；完成必须打到完成端点；回写必须带上未知字段。

**纯函数直接测，不经过 UI**：视图求值（过滤 + 排序）、逻辑日、时间的格式化与解析、优先级标记、深链拼装。

**沿用 v1 的测试资产**：v1 有 521 条测试，其中 318 条不依赖界面（API 客户端、存储、配置、逻辑日、日期解析器、同步引擎、传输守卫），这些直接留。界面相关的 203 条随重写作废，但其中约 50 条其实是引擎/API 级断言，**先把它们搬到不依赖界面的测试文件里再删**，不要连结论一起丢掉。

**新增的验收项**（这三条是这次调查里最容易漏、而且漏了会静默出错的）：

- **中文输入**：能用输入法在标题/描述/备注里打进一段长中文（超过四个汉字），内容是原文而不是转义序列。
- **键位表守卫**：一条测试断言键位表里不出现 `ctrl+enter` 这类不可靠的键——它是防回归的，不是防今天的。
- **收集箱归类**：假后端返回一个形如 `inbox` 加数字的 projectId，断言任务被正确归到收集箱行下；另一个测试断言拿字面量 `"inbox"` 比对时**不会**被当成正确实现。
- **取消完成**：断言它是真的一条独立的写路径，而且取消完成后本地不再把它算作已完成（即使它的完成时间戳还在）。

## Out of Scope

- **日期解析器**：不做自然语言日期输入。新建只填标题，改截止时间走结构化选择器。v1 的这一整块（含它的 75 条测试）作废。
- **v1 的其它界面能力**：优先级循环键 `p`、`/` 模糊过滤、右栏常驻详情、三栏响应式降级、已完成的折叠页脚——都不迁移。
- **不做的功能面**：附件、评论、日历视图、看板视图、番茄钟、习惯、倒计时。
- **只读的字段**：提醒与重复规则只看不改；子任务只看不勾（也不能增删改）。
- **标签的增删**：能打已有的标签，不能在客户端里新建标签，更不能删除（API 也没有删除端点）。
- **清单的手动排序与拖拽**：不写 `sortOrder`，客户端的排序是算出来的。
- **项目组的增删改**：只把已有分组显示成小标题（API 的清单创建与更新接口都不接受 `groupId`，做不到）。
- **把视图同步到服务端**：那条路不存在。
- **多账户 / 多 token**。
- **守护进程与开机自启**。
- **离线写操作的永久队列**：断网时排队重试，但不承诺跨机器或多端合并语义。

## Further Notes

### 这份 spec 取代 issue #1

v1 的 spec（issue #1）通篇建立在「今日执行台」这个定位上，那份定位已被判定不可用。本 spec 取代它；#1 保留作为历史。相关的域名决定记在 `GLOSSARY.md` 与 `docs/adr/`，其中 [ADR-0004](https://github.com/Miaotofu01/Dida-TUI/blob/main/docs/adr/0004-terminal-client-not-today-console.md) 记定位转变，[ADR-0002](https://github.com/Miaotofu01/Dida-TUI/blob/main/docs/adr/0002-immediate-push-irreversible-complete.md) 记「完成不可逆」的推翻，[ADR-0006](https://github.com/Miaotofu01/Dida-TUI/blob/main/docs/adr/0006-disable-kitty-keyboard-protocol.md) 记为什么关掉 kitty 协议推送。

### 已实测的 API 事实（这四条都不是从文档读来的）

1. **取消完成可行**：`task/batch` 的 `update` 带 `status: 0`，回读确认生效。文档对此零提及。
2. **收集箱不在清单索引里**，且它的任务带着一个每账户不同的 `projectId`（形如 `inbox` 加数字）；`inbox` 只是请求侧别名。
3. **`GET /open/v1/project` 的 limit 默认 200**，而客户端现在拿到 `offset`/`limit` 却从不带——第 201 个清单起永远看不见。要修。
4. **`task/filter` 省略 `projectIds` 时返回全部清单加收集箱的任务**（与逐清单拉取逐条一致），但它硬顶 200 条、没有分页，`status: [2]` 在一个已有 200+ 条已完成任务的账户上直接返回满 200 条——**会在不报错的情况下截断**。所以它不能替代逐清单全量。

### 未经验证、实现时要留意的

- 删除一个**清单**时，它里面的任务在服务端会发生什么，文档没写。删除确认的文案必须如实说「不知道」，并且不要承诺任何恢复手段。
- `POST /open/v1/task/{taskId}`（普通更新）能不能单独用来取消完成**没有被单独证实**（实测时任务已经是未完成状态）。已知可行的是 `task/batch` 这条路。实现时别把两者当成等价的。
- `kind` 是 NOTE 的清单长什么样、能不能装任务，没有真实样本可验（账户里只有 TASK 清单）。按「显示但不可进入」实现，遇到反例再改。
- 服务端在写入 `dueDate` 时会**自动补一个同值的 `startDate`**（v1 实测观察）。文档没写，所以不能假定它总会发生，但也不能假定它不会。
- 项目组在真实账户里的行为没有样本（账户里一个组都没有）。按「只显示小标题」实现。

### 一个已知的、故意的取舍

排序改成客户端统一重排之后，网页版上拖出来的手动顺序在终端里不成立；反过来，在终端里新建的任务会拿到一个服务端给的很靠前的 `sortOrder`，所以在网页版上它们排在最上面——两边看到的首屏顺序可能不一致。这是选「按截止时间和优先级排」的代价，不是 bug。

# #46 —— 什么时候重读配置（候选、代价、选择）

工单原文要求：「**何时重读配置由这张工单定**（按 `r`？窗口获得焦点时？文件 watch？），这是一个设计
决定而不是一个补丁——把候选与代价写进工单的收尾说明再选。」

这一页就是那份收尾说明，也是最终的实现说明。**先写候选与代价，再选**；末尾写清楚落地之后的边界。

## 问题的形状（不是「少了一次 reload」）

`config.toml` 只在启动时经 `load_config()` 读一次，`day_end` 在 `SyncEngine.__init__` 里被烤进
`self._day_end`。三处消费者全读这一个字段：

- 「今天」视图 / 逾期判定 —— `read.py` 的 `list_index` / `container_tasks` / `builtin_view_rows`
  （经由 `engine.view()` / `list_index()` / `tasks_in()`）；
- 顺延 —— `schedule.py` 的 `_defer_changes` / `_logical_day_after`；
- 状态栏那一格 —— `engine.status()`。

所以「重读」不是加一条 reload，而是**给这一层一条能换掉日界的路**，并且让三处一起跟着它走。

而且「逻辑日变了」其实有**两条**路，只有一条是配置：

1. 用户在配置里改了边界值；
2. **钟自己走过了边界**（终端里挂一夜，04:00 到了）。

第二条比第一条更像用户真会撞上的那条，而且它会让屏幕**自相矛盾**：状态栏那一格每一跳都按活钟重算，
行却停在昨天——「今天 3」而实际上只有 1 条还算今天。两条路必须一起收口。

## 候选与代价

| 候选 | 代价 | 用户多久看到变化 |
|---|---|---|
| **A. 只按 `r`** | 零依赖、零线程、零定时器；一次 `stat` | 用户不按就永远不变——「立刻」变成「记得按一下」 |
| **B. 文件 watch**（inotify / `watchdog`） | 一个新依赖；一个后台线程（本地 sqlite 连接**有线程亲和**，回调必须 `call_from_thread` 回事件循环，否则踩 t21 那条拆屏竞态）；编辑器大多是**原子写**（写临时文件 + rename），所以得 watch **父目录**而不是文件本身；平台差异（inotify / kqueue / Windows） | 毫秒级 |
| **C. 窗口获得焦点**（DECSET 1004） | 靠终端**主动发**焦点事件：tmux 要 `focus-events on`、部分终端与 ssh 会话根本不发；用户在**同一个终端里分屏**改配置时一次都不触发 | 切回来才生效，且不可靠 |
| **D. 每秒轮询 + 每次重新解析** | 借用 app **已经有**的 1 秒心跳（`push_tick` 的周期泵）——新依赖 0、新线程 0、新定时器 0；代价是每秒一次「打开 + 解析一百来字节的本地文件」：实测 **25.5 µs/次**，跑满一天 ≈2.2 秒 CPU（0.0025% 的一个核） | ≤1 秒，零操作 |
| **E. 每次读（`status()` / `view()`）都重读** | 把磁盘 I/O 塞进读路径（一秒钟十几次）；引擎得知道配置文件在哪——`docs/architecture.md` 的依赖图里 `config` 只从 `bootstrap` 进来，这是一条**新的依赖边** | 立刻，但代价落在了错的层 |

## 选择：**D + A**，并且两条触发共用一个入口

- **D 是主力**：配置文件的改动是**外部事件**（用户在另一个窗口里改），所以「定期看一眼」是唯一不
  依赖用户动作、也不依赖终端能力的做法。它的价格低到可以忽略，因为它**不新增任何机制**：app 本来
  就有一个 1 秒的心跳（t21 的重试泵），两条路都搭在它上面。
- **A 是兜底**：`r` 本来就是用户嘴里那句「现在再看一眼」，同一个检查挂在它上面是免费的，而且它覆盖
  D 的一个真实缺口——**泵是可以不挂的**（`DidaApp(push_tick_seconds=None)`，那也是构造 app 的默认
  值）。只有 D 的话，「日界立刻生效」会悄悄绑死在「重试泵开着」这个策略上。
- **B 与 C 明确不选**：B 的价格（依赖 + 线程 + 原子写 + 平台）远高于它买到的延迟差（毫秒 vs 一秒）；
  C 买不到它承诺的东西（见上表的触发条件），而且失败方式是静默的。
- **E 不选**：它把「配置在哪」这条知识塞进引擎，换来的是把 I/O 放进读路径——层次错了。

**没做 `stat` 门。** 「先比 `st_mtime_ns` 再决定要不要解析」省下的是几十微秒，换来一类**静默漏读**：
改动正好落在上一次 `stat` 的同一个时钟粒度（jiffy，1–4 ms）里，就再也看不见了。25 µs 换掉一个
0.4% 概率的「改了没反应」，值。「值有没有变」由下游判断（`set_day_end` 会说），读手只管读。

### 落点：一个入口，两个键，网络之前

两条路都收口在 `DidaApp.reload_day_boundary()`，挂在 `push_tick`（1 秒心跳）与 `action_refresh`
（`r`）的**最前面**——都在任何网络调用之前。这不是顺手，是因为 `_sync()` 里的重画在 `else:`
（同步成功）那一支里：刷新抛 `DidaError`（断网、凭据失效）时 `refresh_view()` **一次都不跑**，而
收尾的 `update_status()` 照样按新逻辑日写状态栏。判定要是挂在同步的收尾里，「没网的时候按一下 `r`」
就正好得到那个自相矛盾的屏幕。挂在最前面，成不成功都与它无关。

滚过那条**不在 `if self._day_boundary is None` 后面**：它不是配置事件，一个没建读手的 app
（`day_boundary=None`）照样得发现它。屏幕靠 `_view_day` 记住「这一屏是哪一天的」，心跳拿它与
`SyncEngine.logical_day()` 比。

新增的那一口是**便宜的**那一口：`logical_day()` 只有注入的钟与当前日界（实测 **5.5 µs、零 I/O**），
而不是 `status()`（实测 **13.7 µs**，内含 `sync_state()` 的两条 SQL）——一秒问一次的东西不该为了让
状态栏好看多读一次库。`status()` 与 `set_day_end()` 的行为一个字都没改。

## 已知的边界（写下来，不假装它不存在）

- 轮询的粒度就是泵的粒度（生产 `PUSH_TICK_SECONDS = 1.0`）。配置改完、或者钟走过边界之后，屏幕最多
  1 秒跟上。
- 配置文件**读不了**（写坏了、权限不对、被删了、路径上不是文件）时**沿用上一次那个日界**，不崩、
  也不替用户重写一份默认配置（`load_config()` 有「缺文件就生成一份」的行为，轮询这条路不触发它）。
- 滚过只在**同一逻辑日没变**时什么都不做——反向也钉了测试：钟在同一个逻辑日里往前走，这一跳一个
  字符都不重画（否则就是拿一个 bug 换一个性能洞）。
- `_view_day` 记在**画行之前**：反过来的话，边界正好在这几句里跨过去时会记下一个比行更新的日子，
  那一屏就永远没人认领了。记早了最多多画一次，记晚了就是一屏昨天的东西。
